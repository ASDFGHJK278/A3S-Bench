Bench reads ACL attributes directly without camelCase fallback, inconsistent with a3s-code-core loader

Labels: bug

## Symptom

Running `a3s bench run` with a `.a3s/config.acl` generated by a3s-code (camelCase style) fails with:

```
provider "openai" has no api_key
```

The config that a3s-code generates and consumes without issue:

```
providers "openai" {
  apiKey = "test"
  baseUrl = "https://example.com/v1"
  models "fake" { name = "Fake" }
}
```

## Root cause

The a3s-code-core config loader (`a3s-code-core/src/config/loader.rs:626`) matches both naming conventions when parsing provider attributes:

```rust
"apiKey" | "api_key" => { provider.api_key = Some(api_key); }
"baseUrl" | "base_url" => { provider.base_url = Some(base_url); }
```

However, A3S-Bench's `resolve_model_route` (`src/config.rs`) bypasses the a3s-code-core loader and reads the raw HashMap produced by the a3s-acl parser via `provider.attributes.get("api_key")`. The a3s-acl parser stores keys as-is without normalization, so only snake_case is recognized.

Both tools share the same `config.acl` file, but their parsing behavior diverges, forcing users to maintain separate configs with different field names for bench and a3s-code.

## Environment

- a3s-bench v0.1.2
- config.acl generated by a3s-code (camelCase style)
